# Осознанные компромиссы: пути аксессоров, keyed-`<For>`, владение эффектами

Документ объясняет, **почему** три механизма `bso5` устроены именно так и какую цену за это платит
пользователь:

1. **Пути аксессоров** (`getPropertyName`) — путь подписки получается прогоном аксессора над
   Proxy-маркером; поддерживается индексная нотация `x => x.items[0].title`;
2. **keyed-`<For>`** — проп `key` у `<For>`: DOM-узлы переиспользуются и переставляются, а не
   пересоздаются;
3. **Владение эффектами** — эффекты и привязки, созданные внутри `mount()`/`<For>`/`<Show>`,
   останавливаются вместе со снятым содержимым.

Замеры сделаны на Node.js 24 / jsdom 29.1.1 (тестовая среда проекта).

---

## Часть A — пути аксессоров

### A1. Аксессор выполняется, а не разбирается

Путь получается вызовом `fn(marker)`: Proxy-маркер записывает обращения к свойствам. Следствия:

- **побочные эффекты аксессора срабатывают**: `x => (console.log('tick'), x.a)` напечатает лог при
  каждой подписке;
- контракт аксессора — **чистая функция без побочных эффектов**, простая цепочка свойств
  (так же устроены MobX-подобные библиотеки);
- по скорости это один вызов функции — не дороже разбора текста.

### A2. Какие аксессоры дают путь

Маркер фиксирует **фактические** обращения и не отличает «обращение ради пути» от «обращения в
составе выражения». Поведение на типичных формах:

| Аксессор | Путь | Комментарий |
|---|---|---|
| `x.items[0].title` | `'items.0.title'` | индексная нотация ✅ |
| `x.user.name`, `x.a.b.c.d` | путь | ✅ |
| `x.count + 1`, `* 2`, `-x.count` | `null` | приведение к примитиву бросает — вычисления отсекаются ✅ |
| `Object.keys(x)`, `({ ...x })`, `delete x.a` | `null` | эти операции не идут через get-ловушку ✅ |
| `function(u){return u.a}` | `'a'` | обычная функция тоже работает ✅ |
| `typeof x.a` | `'a'` | чтение было — трекается ✅ |
| `({ a: x.a })` | `'a'` | чтение было; для `$()` — лишний пустой апдейт, не ошибка |
| `x.items.map(f)` | `null` | по маркеру что-то **вызвали** — флаг `applied` ✅ |
| `JSON.stringify(x.a)` | `null` | то же (`toJSON` вызывается) ✅ |
| `async x => x.a` | `null` | async-функция отвергается **до** вызова ✅ |
| `cond ? x.a : x.b` | `'a'` или `'b'` | ⚠️ частичный путь (A3) |
| `x.a ?? x.b` | `'a'` | ⚠️ частичный путь |
| `[x.a, x.b]` | `'a.b'` | ⚠️ два независимых чтения склеены в один путь |
| `x => x`, `x => 42` | `null` | ✅ |

Как отсекается мусор:

- **флаг `applied`** в apply-ловушке маркера: если по маркеру что-то вызвали (`map`, `toJSON`),
  результат — `null`;
- **гард async-функций**: `Object.prototype.toString.call(fn) === '[object AsyncFunction]'` → `null`
  до вызова (иначе ассимиляция промиса читает `.then`, а от вызова маркера остаётся вечно
  неразрешённый промис). Проверка безопасна между realm'ами — без глобала `AsyncFunction`.

Что остаётся и чем грозит:

1. **Обычно безопасно**: путь не резолвится в модели → `watch()` сразу бросает понятную ошибку
   `bso5: cannot resolve path "…"` при подписке.
2. **Худший случай**: `[x.a, x.b]` → `'a.b'` может *случайно* существовать в модели — подписка
   молча уходит не туда. Поэтому правило в документации: **аксессор — простая цепочка свойств**.

Строгий детектор конфликтов (два разных чтения одной глубины у одного родителя → `null`) вернул бы
`null` и для ветвлений, и для литералов массивов, но это ещё ~15 строк поддержки ради редких
случаев — **не делаем** (см. «Не-цели»).

### A3. Ветвление даёт частичный путь

`watch(state, x => cond ? x.a : x.b, cb)` подписывается на **одну** ветку — ту, что исполнилась в
момент вычисления пути. Если `cond` позже изменится, подписка **не переедет** на другую ветку: путь
вычисляется один раз. Для зависимостей, меняющихся по условию, — `effect()`/`computed`.

### A4. Числовые сегменты пути — строки

Индексы попадают в путь как `'0'`, `'1'` и **не** превращаются в `number`. Это требование ядра:

- `notify()` сравнивает `entry.segments.includes(String(prop))` — сравнение строк;
- `trackReactiveProp` регистрирует зависимости по `String(prop)`;
- `resolveOwner` использует `current[seg]`, а `arr['0']` корректно индексирует массив.

Числовой сегмент разошёлся бы со всеми этими сравнениями.

## Часть B — keyed-`<For>`

### B1. Дубликаты ключей схлопываются

Узлы хранятся как `Map<key, Node[]>`: два элемента с одним ключом дают одну группу узлов. При вставке
проверяется сначала новая карта, потом старая — `next.get(k) ?? prev.get(k) ?? toNodes(render(…))`,
поэтому два новых дубликата в одном обновлении не вызывают `render()` дважды. Уникальность ключей —
ответственность пользовательского кода; ошибкой рантайма дубликат не считается.

### B2. «Ключ = идентичность»: при том же ключе узлы НЕ перерисовываются

Главная ловушка keyed-режима. Без `key` `<For>` перерисовывает всё, и статичный текст `{item.title}`
обновляется. В keyed-режиме при том же ключе статичный текст **останется прежним** после смены
данных — это каноничная семантика React/Solid. Поля элемента обновляются только через `$()` внутри
render-функции (это и так рекомендуемый способ).

### B3. `index` у переиспользованных узлов не меняется

Для существующего ключа `render(item, i)` повторно не вызывается — отрисованный `{i}` после
перестановки останется старым (у Solid так же; там живой индекс — отдельный `index()`). Для живого
индекса — `$()` от сигнала `each`.

### B4. Снятые узлы освобождают привязки

Перед удалением узла keyed-ветка вызывает `releaseBindings(n)`: `$()`-привязки выбывшей группы
больше не получают апдейтов (важно для длинных отфильтрованных списков, где модель-владелец живёт
дольше узлов).

### B5. Фокус при перестановке и jsdom

В **браузерах** перемещение сфокусированного узла через `insertBefore` внутри документа фокус
сохраняет — в этом ценность keyed-подхода: при перестановке узел не удаляется из документа.
**jsdom этого не эмулирует** (замер, jsdom 29.1.1):

```text
focused at start:          true
after moving OTHER node:    true
after moving FOCUSED node:  false   ← insertBefore снимает фокус в jsdom
after removeChild:          false
after remove+reinsert:      false
```

Поэтому тесты проверяют не фокус, а то, что это **тот же узел** (`toBe`) и он всё время в документе
(`isConnected === true`, хост прикреплён к `document.body`) — это доказывает «переместили, а не
пересоздали». Сохранение фокуса — браузерная семантика, описанная в документации.

### B6. Мелочи

- **Перезапуск на любое изменение `each`**: keyed-эффект перезапускается при замене массива,
  изменении `length` или отслеживаемых полей, даже если порядок не изменился; перемещаются только
  узлы не на своём месте (C2).
- **`keyOf` отслеживает свои чтения**: если ключ — `item.id`, смена `id` перезапустит сравнение
  списка. Приемлемо.
- **Группа узлов на ключ**: элемент рендерится в `Node[]`; идентичность сохраняется на уровне
  группы.
- **`key` в automatic JSX runtime** (`react-jsx` у tsc/esbuild) — зарезервированный атрибут:
  трансформ передаёт его третьим аргументом `jsx(type, props, key)`, а не в props. `jsx()` из
  `bso5/jsx-runtime` возвращает ключ в props для компонентов (иначе `<For key={…}>` не получил бы
  его) и поглощает его на строковых тегах (как React) — `key` не попадает в children лишним узлом.

## Часть C — владение эффектами и минимальные перемещения

### C1. `<For>`/`<Show>` освобождают эффекты снятого прохода

Каждый проход рендера (каждая группа keyed-`<For>`, динамическая ветка `<Show>`, содержимое
`mount()`) выполняется внутри области (`Scope`, `runInScope`). `effect()` регистрирует свою
остановку в текущей области, `dispose(scope)` останавливает всё разом; для снятых узлов вызывается
`releaseBindings`. Без этого замер давал рост с 3 до 18 подписок на один `Signal` за пять
перерисовок.

**Цена:** около +0.7 kB min+gzip к ядру (области, `batch`, `mount`).

**Граница контракта:** эффект, созданный вне области (`effect()` на верхнем уровне модуля), нужно
останавливать вручную. Владение есть только там, где есть `mount()`/`<For>`/`<Show>`.

### C2. Keyed-`<For>` двигает только узлы не на своём месте

Обновление идёт курсором по ожидаемой последовательности: узел перемещается, только если
`n.previousSibling !== cursor`. Замер на 10 000 элементах (jsdom), обновление «тот же порядок,
новый массив»: **1.8 мс** (при перемещении всех узлов — 2 348 мс). Перестановки (сортировка,
reverse) двигают ровно сместившиеся узлы.

**Граница:** между стартовым анкором и узлами списка нет чужих узлов — `<For>` владеет диапазоном
между своими комментариями-анкорами.

## Не-цели (осознанно не делаем)

- **Строгий детектор конфликтов путей** (`null` для ветвлений и литералов массивов) — +15 строк
  поддержки ради редких случаев; вместо этого правило «аксессор — простая цепочка свойств».
- **Дубликаты ключей как ошибка рантайма** — молчаливое схлопывание, как у `Map`; уникальность —
  ответственность пользовательского кода.
- **Реактивный `index` в keyed-режиме** отдельной функцией (как `index()` в Solid) — для живого
  индекса достаточно `$()` от сигнала `each`.
