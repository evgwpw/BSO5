# Осознанные компромиссы: keyed-`<For>` и Proxy-трейсинг путей

Контекст: по итогам сравнения реализаций `bso5` (GLM vs DS) запланировано перенять
два решения из альтернативной реализации:

1. **keyed-`<For>`** — проп `key` у `<For>` с переиспользованием и перестановкой
   DOM-узлов вместо полного пересоздания;
2. **Proxy-трейсинг путей** — замена regex-разбора `getPropertyName` на прогон
   аксессора над Proxy-маркером (поддержка индексной нотации `x => x.items[0].title`).

Этот документ — карта **всех** компромиссов этих изменений, включая те, которых
нет в исходной инструкции, с эмпирическими замерами (зонды прогонялись на
Node 24 / jsdom 29.1.1 — актуальной тестовой среде проекта) и матрицей принятых
решений на имплементацию.

---

## Часть A — Proxy-трейсинг `getPropertyName`

### A1. Аксессор теперь *выполняется*, а не парсится

Старый код разбирал текст функции регуляркой — функция никогда не вызывалась,
побочные эффекты были невозможны в принципе. Новый код реально гоняет `fn(marker)`.
Фундаментальный сдвиг контракта:

- **Сайд-эффекты аксессора срабатывают**: `x => (console.log('tick'), x.a)`
  напечатает лог при каждой подписке. Старая версия просто отвергала такой
  аксессор (`null`).
- Контракт меняется с «синтаксически простая цепочка» на **«чистая функция без
  побочных эффектов»**. Это единственный реальный плюс старого подхода, и он
  теряется — цена принята осознанно (так работает DS и mobx-подобные либы).
- Производительность сопоставима (один вызов функции vs regex + replace +
  две проверки) — не компромисс, а паритет.

### A2. «Правдоподобный мусор» вместо честного `null`

Proxy-трейсинг фиксирует **фактические** обращения к свойствам и не умеет
отличать «обращение ради пути» от «обращение в составе выражения». Замер
на 23 формах аксессоров:

| Аксессор | Было (regex) | Станет (Proxy) | Вердикт |
|---|---|---|---|
| `x.items[0].title` | `null` | `'items.0.title'` | **целевая фича** ✅ |
| `x.user.name`, `x.a.b.c.d` | путь | тот же путь | паритет ✅ |
| `x.count + 1`, `* 2`, `-x.count` | `null` | `null` | ToPrimitive бросает — вычисления отсекаются ✅ |
| `Object.keys(x)` | `null` | `null` | ownKeys не через get-trap, `touched` не срабатывает ✅ |
| `({ ...x })` спред | `null` | `null` | спред не читает через get ✅ |
| `delete x.a` | `null` | `null` | deleteProperty не через get ✅ |
| `function(u){return u.a}` | `null` | `'a'` | statement-форма теперь работает — скорее плюс ✅± |
| `typeof x.a` | `null` | `'a'` | чтение было — трекать `'a'` даже честнее ✅± |
| `({ a: x.a })` | `null` | `'a'` ⚠️ | **существующий тест `reactive.test.ts:35` перевернётся** |
| `cond ? x.a : x.b` | `null` | `'a'` / `'b'` | частичный путь ⚠️ |
| `x.a ?? x.b` | `null` | `'a'` | частичный путь ⚠️ |
| `x.items.map(f)` | `null` | `'items.map'` | apply-trap «пропускает» вызов метода ⚠️ |
| `JSON.stringify(x.a)` | `null` | `'a.toJSON'` | builtin щупает `.toJSON` ⚠️ |
| `async x => x.a` | `null` | `'a.then'` | ассимиляция промиса читает `.then` ⚠️ |
| `[x.a, x.b]` | `null` | `'a.b'` ⚠️⚠️ | **два независимых чтения склеены в один путь** |
| `x => x`, `x => 42` | `null` | `null` | паритет ✅ |

Три уровня ущерба от мусорных путей:

1. **Безопасно** (большинство): путь не резолвится в модели → `watch()` бросает
   понятную ошибку `bso5: cannot resolve path "items.map"` **прямо при подписке**.
   Пользователь сразу видит проблему.
2. **Неприятно**: `[x.a, x.b]` → `'a.b'` может *случайно* существовать в модели →
   подписка молча уходит не туда. Худший случай.
3. **Спорно-полезно**: `({ a: x.a })` → `'a'` — чтение `a` действительно
   произошло; трекать его реактивно корректнее, чем старый строгий `null`.
   Для `$()` это даст лишний пустой апдейт (значение-объект не меняется), но не ошибку.

**Вариант B (принят в имплементацию): флаг `applied` в apply-trap** (~10 строк
поверх drop-in из инструкции): если по маркеру что-то *вызвали* — вернуть `null`.
Убивает три из четырёх мусорных строк (`items.map`, `a.toJSON`, `a.then`),
не трогая целевую фичу. Останутся `cond ? a : b`, `a ?? b`, `[x.a, x.b]`.

Существует и полный вариант ужесточения (depth-conflict: два разных гета с одной
глубины одного родителя → `null`, ~15 строк) — возвращает старую строгость для
ветвлений и массивных литералов, но это заметное отклонение от DS-решения и его
сложнее поддерживать. **Решение: не делать**, покрыть докой «аксессор — простая
цепочка свойств».

### A3. Ветвление даёт частичный путь

`watch(state, x => cond ? x.a : x.b, cb)` подпишется на **одну** ветку — ту, что
исполнилась в момент трейсинга. Если `cond` позже flips — подписка **не переедет**
на другую ветку (`getPropertyName` вызывается один раз). Старая версия отвергала
такой аксессор целиком (`null`). Это задокументировано в исходной инструкции;
вариант B (флаг `applied`) не влияет на этот случай.

### A4. Числовые сегменты остаются строками — не компромисс, а требование

Индексы попадают в путь как `'0'`, `'1'` и **не** конвертируются в `number`
(в отличие от DS). Это требование согласованности с текущим ядром GLM
(проверено по коду `src/reactive.ts`):

- `notify()` сравнивает `entry.segments.includes(String(prop))` — сравнение строк;
- `trackReactiveProp` регистрирует зависимости по `String(prop)`;
- `resolveOwner` использует `current[seg]`, а `arr['0']` корректно индексирует массив.

Числовой сегмент разъехал бы со всеми сравнениями. Ломать нельзя.

## Часть B — keyed-`<For>`

### B1. Дубликаты ключей схлопываются — с нюансом, которого нет в инструкции

`Map<key, Node[]>` — два элемента с одним ключом дают одну группу узлов (как у
DS). Но drop-in код проверяет `prev.get(k)`, а не `next.get(k)`: **два новых
дубликата в одном обновлении** вызовут `render()` дважды, первый результат будет
создан, но никогда не вставлен (мусор для GC, сайд-эффекты рендера сработали зря).
Микро-фикс (гигиенический, не поведенческий): в вставке проверять
`next.get(k) ?? prev.get(k) ?? toNodes(render(items[i], i))`.

### B2. «Ключ = идентичность»: при том же ключе узлы НЕ перерисовываются

Самый важный пользовательский сдвиг. Текущий `<For>` переваривает всё — полный
ре-рендер обновляет и статичный текст `{item.title}`. В keyed-режиме статичный
текст **останется навсегда устаревшим** после смены данных при том же ключе.
Это каноничная семантика React/Solid, но для GLM-аудитории это новая ловушка:
единственный способ обновлять поля элемента — `$()` внутри render-функции
(что и так рекомендуется докой). Обязателен к документированию рядом с `<For>`.

### B3. `index` замораживается для переиспользованных узлов

`render(item, i)` не вызывается повторно для существующего ключа → отрендеренный
`{i}:` не изменится после reorder'а. У Solid аналогично (их `index()` реактивен
отдельно). Старый полный ре-рендер индекс обновлял. Документировать: «в
keyed-режиме отображаемый индекс статичен; для живого индекса — `$()`».

### B4. Удаляемые узлы не проходят `releaseBindings()`

`host.removeChild(n)` в keyed-ветке не останавливает `$()`-биндинги выбывшей
группы — они продолжают получать апдейты, пока жив owner-объект в модели
(типичный кейс — фильтрация длинного списка). **Это не регрессия** — `clearBetween`
в текущем коде делает то же самое, — но именно keyed-режим делает долгоживущие
отфильтрованные списки типовым сценарием. **Принятое решение:** вызывать
`releaseBindings(n)` перед `removeChild` **только в новой keyed-ветке** (старый
путь не трогаем — нулевой риск регрессии для существующих тестов).

### B5. Фокус и jsdom — эмпирическое ограничение тест-плана

Замер в jsdom 29.1.1 (тестовая среда проекта):

```text
focused at start:          true
after moving OTHER node:    true
after moving FOCUSED node:  false   ← insertBefore снимает фокус в jsdom
after removeChild:          false
after remove+reinsert:      false
```

В **реальных браузерах** перемещение сфокусированного узла `insertBefore` внутри
документа фокус сохраняет (это и есть ценность keyed-подхода — узел при reorder'е
никогда не удаляется из документа). jsdom это **не симулирует**. Следствия:

- библиотека корректна: узел при reorder'е только перемещается (`isConnected`
  остаётся `true` на всём протяжении, ни одного remove/recreate);
- **тест «фокус переживает reorder» из исходной инструкции в jsdom написать
  нельзя** — он будет красным не из-за кода, а из-за эмулятора. Честная замена:
  ассерт `toBe` (тот же DOM-узел) + `input.isConnected === true` после reorder
  (доказывает move-not-recreate), а сохранение фокуса — в док как браузерная
  семантика.

### B6. Мелкие следы компромисса (для полноты)

- **O(n)-бухгалтерия на каждый чих списка**: keyed-effect перезапускается на
  любое изменение `each` (замена массива, `length`, затреканные пропы), даже
  если порядок не изменился; `insertBefore` вызывается для каждого узла
  (no-op-перемещение дёшево, но не бесплатно). DS аналогичен.
- **`keyOf` трекает свои чтения внутри effect'а**: если ключ это `item.id`,
  редкая смена `id` перезапустит весь keyed-diff. Приемлемо.
- **`start`-анкор в keyed-ветке не используется** (нужен только `end`) —
  оставляем для единообразия с GLM-стилем, +1 мёртвый comment-узел.
- **Группа узлов на ключ**: GLM рендерит элемент в `Node[]`, DS — в один узел.
  Идентичность сохраняется на уровне группы; внутри группы всё как было.

### Не-цели (осознанно НЕ делаем)

- **Depth-conflict-детект** (строгий `null` для ветвлений и массивных литералов) —
  отклонение от DS-решения, +15 строк поддержки ради редких кейсов.
- **Ключи-дубликаты как ошибка рантайма** — молчаливое схлопывание, как у DS и
  `Map`-семантики; валидация уникальности — ответственность пользовательского кода.
- **Реактивный `index` в keyed-режиме** — отдельной фичей (solid-style `index()`)
  не вводим; для живого индекса достаточно `$()` на `each`-сигнал.

### Проверочные замеры (среда)

- Node.js v24.13.0, jsdom 29.1.1 — версия тестовой среды проекта на момент
  написания; поведение фокуса при `insertBefore` проверено прямым зондом
  (см. B5), таблица `getPropertyName` — прогоном 23 форм аксессоров

  существующим тестам `tests/reactive.test.ts:13–35`).

## Ревью-приписка (Claude Opus 4.8, внешний обзор)

> Эту секцию дописал **я, Claude (Opus 4.8, 1M context)** — как внешний ревьюер,
> сверив документ с фактическим кодом GLM и перепроверив таблицу A2 собственными
> зондами на Node.js v24. Это не правка авторского текста выше, а отдельная
> пометка «проверено».

**Подтвердилось (воспроизведено):**
- **Базовая колонка A2** («Станет Proxy») — точна на 100%, включая
  контринтуитивную `async x=>x.a → "a.then"`: `.then` читается синхронно как Get
  внутри резолва промиса, а сам вызов уходит в микротаск. `x.count+1`,
  `Object.keys(x)`, `{...x}` → `null`; `[x.a,x.b]` → `"a.b"`; `x.items.map` →
  `"items.map"` — всё сходится.
- **B1** (двойной `render()` на дубликатах ключа) — реальный баг; фикс
  `next.get(k) ?? prev.get(k) ?? …` корректен.
- **B4** — инфраструктура `registerBinding`/`releaseBindings` уже присутствует в
  текущем `src/dom.ts` (её используют `boundTextNode`/`applyAttr`/`setStyleProp`),
  поэтому вызов в keyed-ветке — действительно малая правка.
- **A4** — числовые сегменты как строки: верно и необходимо; `pathSubs` уже
  хранит `segments`.

**Найденная неточность (по существу):**
- **A2, вариант B, флаг `applied` НЕ убивает `a.then`.** Текст утверждает, что
  вариант B «убивает три из четырёх мусорных строк (`items.map`, `a.toJSON`,
  `a.then`)». Зонд с вариантом B:

  ```text
  x.items.map(f)  → null      ✅ убит
  JSON.stringify  → null      ✅ убит (a.toJSON)
  async x=>x.a    → "a.then"  ❌ НЕ убит
  ```

  Причина: `.then` — это Get, а не Call; синхронного вызова `.then` не происходит
  (он откладывается в микротаск-джоб), поэтому apply-trap не срабатывает и
  `applied` остаётся `false`. **Вариант B убирает 2 из 4, а не 3** — в списке
  «останутся…» к `cond?a:b`, `a??b`, `[x.a,x.b]` нужно добавить `async → a.then`.
  Практически несущественно (никто не пишет `watch(state, async x => …)`), но
  утверждение фальсифицируемое и оказалось ложным.

**Статус на момент ревью:** сами две правки ещё не внедрены — `getPropertyName`
всё ещё regex-версия, у `<For>` нет пропа `key`; тестов в наборе — 114 (зелёные).
Это соответствует характеру документа (предварительный анализ), фиксирую для
ясности. Пункт **B5** (jsdom снимает фокус при `insertBefore`) я отдельным зондом
не перепроверял — но рекомендация тестировать identity (`toBe`) + `isConnected`
вместо фокуса верна независимо от точных цифр.

— *Claude (Opus 4.8), ревьюер* 🤖

## Приписка после имплементации (GLM, act mode)

Оба изменения внедрены по финальному дизайну выше; `npm run typecheck`,
`npm test` (121 тест, было 114) и `npm run build` — зелёные. Отклонения от
исходной инструкции — ровно согласованные в Части C:

- `getPropertyName`: Proxy-трейсинг + флаг `applied` + AsyncFunction-гард.
- keyed-`<For>`: B1-микрофикс (`next.get(k) ?? prev.get(k) ?? …`) и
  B4 (`releaseBindings(n)` перед `removeChild` в keyed-ветке).
- B5: тест фокуса заменён на identity (`toBe`) + `isConnected` (host
  приаттачен к `document.body` — `isConnected` осмысленен только в дереве).

**Найдено при имплементации (в инструкции не было):** в automatic JSX runtime
(`react-jsx` у tsc/esbuild) атрибут `key` — резервированный: трансформ
передаёт его **третьим позиционным аргументом** `jsx(type, props, key)` и не
кладёт в props. При старом `jsx = createElement` ключ у `<For key={…}>` не
только не доходил бы до компонента, но и **утекал бы в children**. Проверено
зондом esbuild; исправлено в `src/jsx-runtime.ts`: обёртка `jsx()` возвращает
ключ обратно в props для компонентов и потребляет его на строковых тегах
(как React). Это починило и латентный баг: до этого `key` на любом элементе
попадал в children как лишний узел.

Прочее: версия `0.2.0 → 0.3.0` (minor — обратно совместимые фичи), размер
бандла переснят и уточнён в README/`src/index.ts`: `bso5` 9.38 kB min /
**3.39 kB min+gzip** (было ~3 kB), `bso5/jsx-runtime` 2.41 kB / 1.04 kB.

## Верификация ревью (GLM-агент, повторный зонд, Node v24.13.0)

> Ответ на приписку выше. Фальсифицируемое утверждение ревьюера перепроверено
> отдельным зондом (вариант B + таймлайн trap'ов async-аксессора); статус-клаймы —
> грепами по коду.

**Ревьюер прав, воспроизведено:** флаг `applied` НЕ убивает `a.then`. Таймлайн:

```text
sync phase (пока выполняется getPropertyName):  ["get:a", "get:then"]
после дрейна микротасков:                       ["get:a", "get:then", "CALL(marker)"]
```

`.then` — это Get, а сам вызов `.then` откладывается в микротаск и происходит
**после** возврата из `getPropertyName` — `applied` синхронно остаётся `false`.
Утверждение A2 «убивает три из четырёх» ложно, причём вдвойне: (1) `a.then` не
убивался; (2) «четырёх» — небрежный счёт: ⚠️-строк в таблице A2 шесть.
Вариант B **один** убивает 2 из 6 (`items.map`, `a.toJSON`); остаются
`cond ? a : b`, `a ?? b`, `[x.a, x.b]` **и `async → 'a.then'`** — как и пишет
ревьюер.

**Завершающий фикс (финальный дизайн):** builtin-тег async-функции —
realm-безопасно через `Object.prototype.toString.call(fn)` (без глобала
`AsyncFunction`):

```ts
if (Object.prototype.toString.call(fn) === '[object AsyncFunction]') return null;
```

— async-аксессор отвергается **до** вызова. Заметим: старая regex-версия
async-стрелки тоже отвергала (head-регэксп `([\w$]+)\s*=>` не матчит
`async x =>`), так что это **восстановление паритета, не новое ограничение**;
бонус — не остаётся висячего никогда не резолвящегося промиса от вызова
маркера (зонд: `promise ever settled: false`).

**Финальный дизайн `getPropertyName`** = Proxy-трейсинг (drop-in из
инструкции) + флаг `applied` в apply-trap + гард AsyncFunction (~11 строк
сверх drop-in). Итог по таблице A2: убито 3 из 6 ⚠️-строк (`items.map`,
`a.toJSON`, `async`); остаются `cond ? a : b`, `a ?? b`, `[x.a, x.b]` — ровно
те три, что исходный текст (без `async`) заявлял как «останутся».

**Поправка к матрице C, строка A2:** «+ флаг `applied` **и AsyncFunction-гард**

## Часть D — добавлено 2026-11-01: владение эффектами и минимальные перемещения

Две правки закрывают дефекты, найденные пробниками (внешний обзор 2026-11-01).

### D1. `<For>`/`<Show>` освобождают эффекты снятого прохода

**Было:** unkeyed `<For>` при перерисовке делал `clearBetween` и вставлял новые
узлы, но не останавливал эффекты, созданные внутри `render()`, и не вызывал
`releaseBindings` для снятых узлов. Замер: 3 → 18 подписок на один `Signal` за
пять перерисовок; шесть «мёртвых» эффектов срабатывали на одну запись.

**Стало:** каждый проход рендера (и каждая группа keyed-`<For>`, и динамическая
ветка `<Show>`) выполняется внутри `Scope` (`runInScope`). `effect()` регистрирует
свою остановку в текущей области, `dispose(scope)` останавливает всё разом;
`releaseBindings` вызывается для снятых узлов.

**Цена:** +0.7 kB min+gzip к ядру (scope, `batch`, `mount`, расширенный
`shouldProxy`) — размер в README вырос с ~3.4 до ~4.7 kB честно.

**Издержка, которую стоит помнить:** область живёт до сноса; эффект, созданный
вне области (`effect()` на верхнем уровне модуля), по-прежнему требует ручной
остановки. Это не регресс, а граница контракта: владение появляется только там,
где есть `mount()`/`<For>`/`<Show>`.

### D2. Keyed-`<For>` двигает только узлы не на своём месте

**Было:** на каждое обновление `insertBefore(n, end)` для всех узлов списка —
даже если порядок не изменился. Замер на 10 000 элементах (jsdom): 2 348 мс за
обновление «тот же порядок, новый массив».

**Стало:** курсор по ожидаемой последовательности; узел перемещается только если
`n.previousSibling !== cursor`. Тот же замер: **1.8 мс**. Перестановки
(сортировка, reverse) по-прежнему двигают ровно те узлы, которые сместились.

**Граница:** курсор предполагает, что между стартовым анкором и узлами списка нет
чужих узлов — в keyed-ветке это гарантировано, `<For>` владеет диапазоном между
своими комментариями-анкорами.
